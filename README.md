# eval-agent

![eval-agent 전체 구조](docs/images/architecture.svg)

평가 데이터를 자연어로 물어보면, LLM이 필요한 도구를 직접 골라 DB를 조회하고 근거와 함께 답해 주는 서비스입니다. Python, LangGraph, MCP로 만들었고, 데이터는 모두 더미입니다.

## 어떤 질문에 답하나

- 2025년 본부별 B등급 비율을 비교해줘
- 영업본부 등급 분포가 작년보다 어떻게 바뀌었어?
- 영업본부 B등급 비율이 높은 게 기준 문서상 허용되는 수준이야?
- 개발본부 다면평가 평균은?
- 2023년 결과 보여줘 (데이터가 없으면 없다고 답해야 합니다)

### 데모 시나리오: 영업본부 B등급

더미 데이터에서 영업본부의 2025년 B등급 비율을 일부러 기준보다 높게 만들어 두었습니다. "영업본부 B등급 비율이 높은 게 기준 문서상 허용되는 수준이야?"를 물으면, 에이전트는 아래 근거를 도구로 확인해서 답합니다.

| 확인할 것 | 쓰는 도구 | 도구가 돌려주는 값 |
|-----------|-----------|--------------------|
| 영업본부 B등급 비율의 변화 | `compare_years` | 2024년 51.7% → 2025년 68.3% (+16.7%p, 세 평가유형 합산 건수 기준) |
| 다른 본부와의 비교 | `get_grade_distribution` | 2025년 성과 기준 개발 48.8%, 경영지원 50%, 생산 51.4% |
| 기준 문서의 허용 범위 | `search_policy_docs` | 영업본부 B등급 상한 65% (일반 가이드는 40~60%) |

이 값만으로는 영업본부가 상한(65%)을 약 3.3%p 넘었다는 것까지만 말할 수 있습니다. 왜 높아졌는지는 데이터에 없으므로, 에이전트는 원인을 추측하지 않고 "추가 확인이 필요합니다"라고 답하도록 만들었습니다.

## 왜 만들었나

- Java/Spring으로만 일해서 Python 경험이 없었는데, Python 프로젝트와 LangGraph, MCP를 처음부터 끝까지 직접 해 보고 싶었습니다.
- 동작하는 코드만이 아니라 "왜 이렇게 만들었는지"를 설명할 수 있게, 단계마다 설계 이유와 한계를 작성했습니다.
- 이전에 [Spring AI로 평가 문의 자동 분류 시스템](https://github.com/kjennn/hr-eval-inquiry-triage)을 만들었는데, 그건 정해진 순서대로 도는 워크플로였습니다. 
- 이번에는 LLM이 어떤 도구를 부를지 직접 고르는 에이전트로 만들어서 둘의 차이를 비교해 보려고 했습니다.

## 사용 방법은 두 가지입니다

같은 도구 4개를 두 가지 방식으로 쓸 수 있습니다.

| | 에이전트 (CLI, API) | MCP 서버 (Claude Desktop/Code) |
|---|---|---|
| LLM | 내 코드가 Claude API를 호출 | 클라이언트(Claude Desktop/Code)의 Claude |
| 필요한 것 | DB, 시드, Claude API 키 | DB, 시드, 클라이언트 설정 |
| 비용 | 호출마다 Claude API 사용료 | 이 서버 자체는 없음 (클라이언트 계정의 사용량) |
| 답변 통제 | 반복 한도, 근거 자동 첨부, "추가 확인이 필요합니다" 규칙을 내 코드가 적용 | 적용되지 않음. 도구 설명만 보고 클라이언트가 답함 |

도구를 제공하는 것과 안전한 답변을 보장하는 것은 별개입니다. 답변 규칙이 중요하면 에이전트 방식으로 쓰고, 편하게 조회만 하려면 MCP로 씁니다.

## 준비물

Python 패키지 관리자 [uv](https://docs.astral.sh/uv/)와 Docker가 설치되어 있어야 합니다.

| 하고 싶은 것 | Docker DB | 시드 | Claude API 키 |
|--------------|-----------|------|----------------|
| 테스트 (`pytest`) | 불필요 (메모리 SQLite) | 불필요 | 불필요 |
| CLI, API | 필요 | 필요 | 필요 (`.env`) |
| MCP 서버 | 필요 | 필요 | 불필요 |

## 빠른 시작

```bash
git clone https://github.com/kjennn/eval-agent.git
cd eval-agent
cp .env.example .env                  # 설정 파일 생성 (.env는 커밋되지 않습니다)
docker compose up -d                  # PostgreSQL 기동
uv sync                               # 가상환경과 의존성 설치
uv run python scripts/seed.py         # 테이블 생성과 더미 데이터 입력
uv run pytest                         # 테스트 (API 호출이나 비용 없음)
```

`seed.py --reset`은 모든 데이터를 지우고 다시 만드니, 데이터가 있는 DB에서는 신중하게 쓰세요.

CLI나 API를 쓰려면 `.env`에 Claude API 키와 모델명을 넣습니다. 모델명은 코드에 기본값이 없어서 `.env`에 꼭 지정해야 합니다. `.env.example`에는 개발용으로 `claude-haiku-5-5`가 적혀 있고, 지원되는 모델명은 바뀔 수 있으니 사용 전에 확인하세요. API 키는 `.env`에만 넣고 코드나 커밋에 넣지 않습니다.

```bash
# 에이전트 (CLI)
uv run python scripts/ask.py "개발본부 다면평가 평균은?"
uv run python scripts/ask.py -v "..."            # -v: 도구 호출 과정을 단계별로 출력

# 에이전트 (API) - 실행 후 http://127.0.0.1:8000/docs 에서 Swagger로 호출해 볼 수 있습니다
uv run uvicorn eval_agent.api.app:app --host 127.0.0.1 --port 8000
```

API는 인증이 없고 호출마다 비용이 드니, 외부에 공개하지 않습니다. Claude Desktop/Code에서 도구를 쓰려면 [MCP 서버 연결 가이드](docs/mcp-setup.md)를 따라 하세요.

## 도구 4개

| 도구 | 하는 일 |
|------|---------|
| `get_grade_distribution` | 연도(와 본부, 평가유형)별 S/A/B/C/D 등급 인원과 비율을 조회합니다. |
| `compare_years` | 한 본부의 두 연도 등급 분포를 비교하고 변화량(%p)을 계산합니다. |
| `get_org_summary` | 한 본부의 인원수, 평균 점수, 평가유형별 평균을 조회합니다. |
| `search_policy_docs` | 기준 문서(등급 배분 가이드 등)에서 관련 문단을 검색합니다. |

Spring에 비유하면 `tools/`가 서비스 계층이고, 에이전트(+API)와 MCP 서버는 같은 서비스를 서로 다른 방식으로 노출하는 컨트롤러입니다.

## 설계 원칙

- **도구는 자유 SQL을 받지 않도록 제한했습니다.** 정해진 파라미터만 받는 읽기 전용 함수입니다. 다만 DB 계정 자체는 읽기 전용으로 분리하지 않았습니다(아래 한계 참고).
- **숫자는 코드가 계산하고 근거도 코드가 붙입니다.** 변화량(%p)은 건수로 코드가 계산하고, 답변 끝의 "어떤 도구를 어떤 조건으로 불렀는지"는 호출 기록에서 뽑아 붙입니다.
- **모르는 것은 모른다고 합니다.** 도구로 확인한 숫자만 사실로 말하고, 데이터에 없는 원인은 "추가 확인이 필요합니다"라고 답합니다.
- **에이전트는 통제하고, MCP는 통제하지 않습니다.** 에이전트에는 반복 한도와 근거 첨부가 있고, MCP로 쓰면 이 규칙이 적용되지 않습니다.
- **개인 이름 없이 집계만 다루고, 데이터는 전부 더미입니다.**

각 결정의 이유는 [설계 결정과 부딪힌 문제](docs/design-decisions.md)에 정리했습니다.

## 검증 현황

2026-10-23 기준입니다. 숫자와 결과는 코드를 고치면 달라질 수 있으니, 직접 `uv run pytest`로 다시 확인하세요.

확인한 것

- `uv run pytest` 전체 통과 (72개). 가짜 LLM, 메모리 SQLite, MCP 클라이언트를 써서 API 호출이나 비용이 들지 않습니다.
- 실제 Claude API로 CLI와 `POST /ask`를 호출해서 테스트 질문의 답변과 근거 첨부를 확인했습니다.
- MCP 서버를 실제 stdio로 띄워 도구 호출을 확인했고, Claude Desktop에 연결해서 질문한 결과 도구를 써서 답하는 것을 확인했습니다.

확인하지 못한 것

- 답변 품질을 체계적으로 평가하지 못했습니다. 테스트 질문 5개 외의 다양한 질문은 해 보지 않았습니다.
- 같은 질문을 반복해서 답변이 안정적인지는 재 보지 않았습니다.

## 한계와 다음 단계

한계

- 인증과 호출 횟수 제한이 없습니다. API는 호출마다 Claude API 비용이 드니 외부에 공개하면 안 됩니다.
- 질문마다 독립 실행이라 대화 기억이 없습니다. "그럼 개발본부는?" 같은 후속 질문을 이해하지 못합니다.
- 기준 문서 검색이 키워드 매칭이라 표현이 다르면 놓칠 수 있습니다.
- DB 계정이 읽기 전용으로 분리되어 있지 않습니다. 도구가 읽기 전용 함수라 지금은 안전하지만, 운영이라면 계정 수준에서도 막아야 합니다.
- 더미 데이터라 규모가 작습니다(250명, 2개 연도). 실제 규모에서의 성능은 모릅니다.

다음 단계

- **평가 세트를 만들어 자동 채점합니다.** 질문마다 아래 항목을 정해 두고 에이전트를 돌려 비교합니다.

  | 평가 항목 | 확인하는 것 | 예 (영업본부 B등급 질문) |
  |-----------|-------------|--------------------------|
  | 기대 도구 | 알맞은 도구와 인자를 골랐는가 | `compare_years(영업본부, 2024, 2025)`, `search_policy_docs` |
  | 기대 수치 | 답변의 숫자가 도구 결과와 같은가 | 68.3%, +16.7%p, 상한 65% |
  | 근거의 정확성 | 첨부된 근거가 실제 호출 기록과 같은가 | 호출한 도구와 조건이 그대로 표시됨 |
  | 원인 추측 여부 | 데이터에 없는 원인을 지어내지 않았는가 | "추가 확인이 필요합니다"로 답함 |
  | 데이터 없음 처리 | 없는 연도에 없다고 답하는가 | "2023년 데이터가 없습니다" |

- 대화 기억(LangGraph 체크포인터), 기준 문서 검색을 임베딩으로 바꾸고 키워드 검색과 비교
- 응답 스트리밍, 인증, 호출 횟수 제한
- 읽기 전용 DB 계정 분리, MCP 서버의 원격(HTTP) 전환
